画面一 · 约20秒

我们关注的是需要处理多个商家退货的网购用户。比如一个学生，购买信息在邮件、小票和截图里，政策与操作步骤又在不同商家页面上。用户需要自己把这些信息拼起来，再决定先做什么。

画面二 · 约25–30秒

Return Pilot 希望将这些购买信息整理成跨商家的退货任务，结合政策和用户的选择，告诉用户现在该做什么，并持续跟进。缺少收货日期时，我们保留未确认状态，先请用户补充。我们的目标是减少查找、记忆和安排退货的负担，帮助用户及时完成必要步骤。这是体验概念，详细操作会在后面的 Web demo 展示。

画面三 · 约35–40秒

从第一次 idea pitch 到现在，我们围绕三条线推进。第一，产品范围。当前原型已把购买确认、退货任务、计划与跟进串成流程，具体商家和支持条件还需要用本阶段范围文档确认。第二，产品体验。我们已经有可点击的 Web 原型，这里是它的真实截图；示例数据与手动更新让核心交互可以演示。第三，AI 评估。我们已用 20 个固定案例比较规则、LLM 和混合方案，接下来展示各自适合承担什么。

Customer persona · Emma · 约30秒

这三个人物是我们拟定的用户与反馈假设，还不是访谈结果。Emma 是经常跨商家购物的研究生。她的痛点不只是忘记截止时间，而是每次退货都要重新翻邮件、小票和政策，才能拼出商品、到货时间和操作要求。第一次点击，把同一批购买凭证变成有顺序的任务；第二次点击强调临近期限的行动，同时保留缺少日期的未确认状态。她预期会满意，因为产品减少了重复查找和自己记忆的负担。

Customer persona · Ryan · 约30秒

Ryan 是重视隐私的软件工程师。他认为产品有用，但担心为了几件退货就授权整个邮箱。第一次点击只突出订单邮件，并显示转发单封订单、上传小票和手动输入三种选择；第二次点击说明这种输入设计不要求全邮箱授权。这是后面 architecture 可以回应的具体访问范围问题，但不是已经完成的安全认证，也不代表加密、删除或数据保留机制已经实现。

Customer persona · Maya · 约30秒

Maya 是在工作与通勤之间办理退货的上班族。网页方便在家规划，但投递和查看凭证发生在外面。第一次点击出现手机端概念，用于查看步骤、拍摄凭证和更新进度；第二次点击把桌面与手机的同一批任务关联起来，作为未来扩展。最后用价值、信任、下一步三个词总结，并衔接后面的 architecture 或 future work。手机端尚未交付，图中是概念。

实验设置 · 约15–20秒

我们只测规划层，把购买背景和政策证据固定在同样的 20 个案例里。四种策略分别是规则、基础提示、结构化提示，以及结构化提示加确定性验证和规则回退；两个模型接受相同输入。这样要回答的是 AI 在哪里真正增加价值。

Prompt engineering · B0 foundation → B1 techniques → measured improvement

First, we tested whether prompt engineering alone could improve planning accuracy. Our baseline prompt already defined the role, task, constraints, and output schema.

For B1, we added structured reasoning, one complete worked example, and an explicit consistency check.

With the same models and the same 20 cases, Qwen improved from 5% to 50%, while GPT improved from 50% to 65%. This suggests that clearer decision structure can significantly improve planning accuracy, although prompt engineering alone does not eliminate errors.

准确率与规则基线 · 约30–35秒

图表先给出 B0、B1、C 在两个模型上的完整结果，规则基线为 20/20。第一步标出结构化提示和确定性验证各自带来的提升；C 是包含规则回退的最终系统正确率。第二步看规则基线达到 20/20 所需的显式检查、分支和例外覆盖。

Token economics · model cost trade-off

Token economics gave us another trade-off. GPT performed better in our evaluation, but it is also around 3.3 times the model API cost of Qwen per case. Qwen B1 costs $0.000570 and C costs $0.000575; GPT B1 costs $0.00189 and C costs $0.00191. The ratios are approximately 3.32 at both B1 and C. Qwen uses approximately 16.5K to 16.7K tokens, a total increase of 202, while GPT uses approximately 16.8K to 17.0K.

Click once to reveal the cross-model comparison. Within each model, moving from B1 to C adds very little model cost because validation runs locally without another LLM repair call. The increments are $0.000005 for Qwen and $0.00002 for GPT per case. These are estimated model API costs, excluding infrastructure, engineering, and broader operating costs.

For the MVP, we may still prioritize reliability, but one optimization opportunity is reducing unnecessary input context, for example retrieving only relevant parts of retailer policies rather than sending all policy content. This does not finalize GPT as our production model or establish that higher cost automatically creates better business value.

Challenges & next priorities · 30–40 seconds

We faced three main challenges. First, our initial prompts were unstructured, so we improved them through structured prompt engineering. Second, GPT performed better, but at about 3.3 times the model API cost. We may still prioritize reliability while reducing unnecessary policy context and input tokens; we have not finalized a production model. Third, we had to decide how to approach customer discovery. We chose interviews with everyday shoppers because this consumer problem benefits from deeper qualitative feedback to shape the MVP.

Click once: next, we want to improve our agent harness through targeted retrieval, context filtering, and tool use; strengthen privacy protections; and explore mobile support. Privacy improvements and mobile remain future work.
